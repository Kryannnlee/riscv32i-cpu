# 09 · 避坑清单（bug 可能性）

> 平时遇到的坑，按"现象 / 原因 / 防范 / 验证"记下来。越攒越值钱。
>
> **真正踩过的那几条**，详细现场在 `cases/`（现象、当时的代码、怎么定位、修正前后对比）。
> 这里只留一句话结论 + 指过去。未踩到的防范条目留在这里。

---

## 1. 隐式网络（implicit nets）→ 高位被截断
- **现象**：编译不报错，但结果错（如 `c` 变成 `3'b001`）。
- **原因**：没声明的信号被 Verilog **偷偷当成 1-bit wire**。
  ```systemverilog
  wire [2:0] a, c;
  assign a = 3'b101;
  assign b = a;   // b 没声明 → 1-bit，b = 1
  assign c = b;   // c = 001 ← bug
  ```
- **防范**：所有信号显式声明；可选文件顶部 `` `default_nettype none ``（恢复用 `` `default_nettype wire ``）。
- **验证**：位宽不匹配时若"编译通过但值不对"，先查信号是否漏声明 / 宽度是否一致。

---

## 2. 组合逻辑漏赋值 → 综合出锁存器（latch）
- **现象**：`always_comb` / `case` / `if` 里某个分支没给输出赋值，综合警告 "inferring latch"。
- **原因**：硬件不知道"其它情况"该怎么办 → 默认"保持原值" → 需要记忆 → 变成 latch。组合逻辑不该记忆。
- **防范**：`case` 写 `default`；`if` 补 `else`；或**进 always 先给所有输出赋默认值**。
- **验证**：看综合/编译警告里有没有 "latch"。

---

## 3. `=`（阻塞）与 `<=`（非阻塞）混用
- **现象**：仿真结果诡异，和预期差一拍。
- **原因**：`=` 立即生效、`<=` 时刻末统一更新；混用破坏"同时更新"语义。
- **防范**：**组合用 `=`，时序用 `<=`**。
- **验证**：同一 always 块里是否两种赋值混着写；时序块里是否误用 `=`。

---

## 4. 位宽不匹配 → 截断 / 补零
- **现象**：值莫名变 0 或变小。
- **原因**：窄的赋给宽的补零，宽的赋给窄的截断，且不一定报错。
- **防范**：注意每根信号的位宽；拼接 `{}`、复制 `{n{}}` 明确宽度。
- **验证**：`-Wall` 打开位宽警告。

---

## 5. 老式敏感列表漏信号
- **现象**：仿真和硬件不一致（硬件对、仿真错）。
- **原因**：`always @(a)` 漏了 `b` → 仿真时 `b` 变不会重算；综合按 `@(*)` 处理。
- **防范**：组合逻辑用 `always_comb`（或 `always @(*)`），别手写信号列表。
- **验证**：检查 always 敏感列表是否手写且可能漏项。

---

## 6. testbench 在时钟沿驱动信号 → 竞争
- **现象**：仿真写入时序偶发不对。
- **原因**：在 `posedge` 同时改输入，和 DUT 采样打架，结果不确定。
- **防范**：testbench 在 **`negedge`** 驱动信号，让它在下一个 `posedge` 前稳定。
- **验证**：看 testbench 是否用 `@(negedge clk)` 驱动。

---

## 7. 字节序混淆（大端 / 小端）
- **现象**：从内存读出的值"看起来颠倒了"，或程序/数据加载后全错。
- **原因**：RISC-V 是**小端**；若按大端手工摆字节，数据全错。
- **防范**：记住 **RISC-V 小端**；`0x00A30293` 存内存 = `93 A3 02 00`。别和网络序（大端）混。
- **验证**：检查指令/数据在内存里的字节顺序；`LW`/`SW` 是否按小端。

---

## 8. 同一信号被多处驱动（multiple drivers）
- **现象**：编译报错 `not a valid l-value` / 多处驱动，或综合结果不确定。
- **原因**：一个信号被多条 `assign` 驱动（或部分位 + 整体同时驱动）。
  ```systemverilog
  assign out[2:0] = a;
  assign out[5:3] = b;
  assign out = c;      // ← 又驱动了整个 out，冲突！
  ```
- **防范**：一个信号**只有一种驱动方式**：要么整体 `assign out = ...`，要么逐段 `assign out[i] = ...`，别混。
- **验证**：搜同一信号是否出现在多个 `assign`/always 的左边。

---

## 9. 部分选择漏驱动 → 未驱动位是 `Z`（不是 latch）
- **现象**：只给向量一部分位赋值，其余位在仿真里是 `Z`，综合警告。
- **原因**：`assign out[15:0] = ...` 只驱动低 16 位，`out[23:16]` 没人驱动。
- **区分**：`assign` 漏驱动 → **高阻 Z**（+综合警告）；**latch 只出现在 `always` 组合块漏赋值**，两者不同。
- **防范**：想清楚是整体赋值还是分段；整体赋值时注意"窄赋宽会自动补 0"。
- **验证**：看仿真波形的 `Z`，或看综合警告。

---

## 10. PowerShell 改 UTF-8 文件 → 中文乱码
- **现象**：用 `Get-Content -Raw | Set-Content` 改带中文的文件后，中文变成乱码。
- **原因**：Windows PowerShell 5.1 的默认编码**不是 UTF-8**（是系统 ANSI），读写 UTF-8 文件会损坏多字节字符。
- **防范**：改带中文的文件，用**编辑器**，或明确指定 `-Encoding utf8`（且读取也要 `-Encoding utf8`）；不确定就别用脚本批量替换。
- **验证**：用 Python `open(path,'rb').read().decode('utf-8')` 检查是否合法。

## 11. 转发条件漏了 `reg_write` → `sw` 的"假 rd"被当成目的寄存器
- **现象**：平时跑得好好的，`sw` 后面跟一条读某个寄存器的指令时结果莫名其妙。
- **原因**：S 型指令**没有 rd 字段**，`instr[11:7]` 装的是立即数的低 5 位。`sw x1, 4(x2)` 的 `instr[11:7] = 4`，看起来就像在写 x4。
- **防范**：转发条件必须写成三条与：`reg_write && (rd != 0) && (rd == rs)`。

---

## 12. 转发条件漏了 `rd != 0` → x0 被污染
- **现象**：读 x0 的指令拿到非 0 值。
- **原因**：`addi x0, x0, 5` 的 rd 是 0，ALU 算出来是 5，转发过去就把"x0 恒为 0"破坏了。
- **防范**：同 11，条件里带 `rd != 0`。

---

## 13. 转发 MUX 放在 ALUSrc 之后 → 立即数被"转发"掉
- **现象**：`addi` / `lw` 这类用立即数的指令结果乱掉。
- **原因**：`alu_b = alu_src ? imm : rs2` 先做了选择，再把转发加在后面，等于把选好的立即数替换成某条无关指令的 ALU 结果。
- **防范**：顺序必须是 **先转发 rs2 → 再 ALUSrc 选择**。

---

## 14. `id_ex` 只存数据不存寄存器编号 → 转发无从比较
- **现象**：想写转发单元时发现手上只有 `rs1_data`，没有 rs1 的编号。
- **原因**：ID 段产生的是数据；编号（`instr[19:15]` / `[24:20]`）需要显式锁进 `id_ex` 才能带到 EX 段。
- **防范**：定 `id_ex` 字段时问一句"后面哪一级还要用这个信息"。

---

## 15. 用两个独立 `if` 写转发条件 → 优先级反了
- **现象**：连续两条指令写同一寄存器时，转发拿到的是**旧**的那条的结果。
- **原因**：两个独立 `if` 顺序执行，后写的覆盖先写的，等于 MEM/WB 优先于 EX/MEM。
- **防范**：用 `if / else if` 表达优先级，EX/MEM 放前面。

---

## 16. 变量名 `expect` 是 SystemVerilog 关键字
- **现象**：`logic [31:0] expect [0:7];` 报 `syntax error in variable list`。
- **原因**：`expect` 是 SVA（断言）里的关键字。
- **防范**：测试里存期望值用 `expected` / `exp_val` 之类。同类关键字还有 `property`、`sequence`、`assume`。

---

## 17. 加了输入端口但例化处没接 → 悬空成 Z，`!Z` 变成 X，PC 卡死
- **现象**：给 `program_counter` 加了 `stall` 输入后，单周期 `cpu_tb` 突然全错，
  只有第一条指令生效，其余寄存器都是 0。没有报错，只是"跑不动"。
- **原因**：`cpu_top` 例化时没写 `.stall(...)`，该输入悬空为 **Z**。
  `else if (!stall)` 里 `!Z` 求值成 **X**，`if` 两边都不成立，于是**不做任何赋值**，PC 保持不动。
- **定位**：先看 PC 是不是不变；再看波形里那个端口是不是 Z。
- **防范**：给模块加输入端口后，全工程搜一遍这个模块名，每个例化点都检查。
  用不上的输入就显式接常量（如 `.stall(1'b0)`），别留空。

---

## 18. 改模块接口 → 所有例化点和 testbench 都要跟着改
- **现象**：改完 RTL，`rtl/*.sv` 编译过，但某些 testbench 结果不对或报错。
- **原因**：testbench 也是"例化点"。新增输入若不接，同样是 Z。
- **防范**：改接口后按这个顺序过一遍：
  1. 全工程 `grep` 模块名，列出所有例化点
  2. 每个例化点补端口
  3. 对应的 `*_tb.sv` 补端口并加一条针对新端口的断言
  4. 跑全套回归，确认没有从 PASS 变 FAIL

---

## 19. 分支目标地址用 `pc` 而不是 `id_ex_pc` → 跳飞 8 字节
- **现象**：分支明明该跳，结果跑到别处去了，或者跳转后执行了一堆无关指令。
- **原因**：分支在 **EX** 级判断时，`pc` 寄存器已经指向它后面第 2 条了。
  用当前 `pc + imm` 算目标，等于多加了 8 字节。
- **正确写法**：`branch_target = id_ex_pc + id_ex_imm`，
  其中 `id_ex_pc` 是这条分支自己的地址（ID 级锁存下来的）。
- **一句话**：流水线里"当前 pc"和"这条指令的 pc"不是一回事，要用哪个想清楚。

---

## 20. 冲刷（flush）必须同时清 ID 级和 EX 级
- **现象**：分支跳转后，被跳过的指令仍然执行了一次（寄存器被写脏）。
- **原因**：只清了 `if_id`，`id_ex` 里那条取错的指令还会照常进 EX 并写回。
- **防范**：分支在 EX 判断时，错的是 **ID 级的那条** 和 **正在取的那条**，
  对应 `if_id` 和 `id_ex` 两个寄存器，两个都要灌气泡。
- **验证**：在分支后面放一条"毒药"指令（写一个特殊值），
  跑完检查那个寄存器没被改。断掉 flush 重跑，毒药值应该出现。

---

## 21. 测试只断言寄存器终值 → 路径错了也照样全绿
- **现象**：把分支目标算错 8 字节（用 `pc` 而不是 `id_ex_pc`），
  15 项寄存器检查**全部 PASS**，只有 `redirect_count` 抓到了。
- **原因**：多跳的那 8 字节恰好越过了毒药区和第二个分支，
  寄存器终值碰巧和正确路径一样。**路径全错，终值相同。**
- **防范**：除了"最后每个寄存器是多少"，还要断言**过程**：
  - 跳转/改道次数
  - 停顿次数
  - 执行的指令条数
  - 内存写入次数
- **进阶**：指令级随机对比测试（同一个程序跑两个 RTL，逐条比寄存器）比手写断言更狠。
- **一句话**：**只比终值，等于只检查了结果，没检查过程。路径错误最爱藏在这里。**

---

## 22. 有跳转的程序，imem 条数 ≠ 执行条数
- **现象**：CPI 算出来 `开销 -12 拍`（实测比"理想"还快），进而得出"加法模型不成立"的结论。
- **原因**：`PROG_LEN` 用的是 imem 里写了多少条（57），
  但 7 处跳转跳过了 8 条，真正执行的是 49 条。分母错了，结论全错。
  另外完成标记盯的 `x30` 在扩程序后已经不在末尾，测的是"跑到一半"。
- **防范**：静态条数和动态条数**分开命名**；CPI 分母永远用 retire 条数。
  预测值要写成**断言**（实测 != 预测就报错），不能只 `$display`。
- **验证**：改完两边都是 68 拍；回头验算老版本 36+4+1+8=49 也对上，
  说明模型一直是对的，[033] 那条结论是假象。
- **档案**：`cases/case-22-static-instr-count-cpi.md`
- **一句话**：**有跳转就有"写了没执行"的指令，分母必须数退休的。**

## 23. 哈佛结构里，`lw` 读不到 `.rodata`
- **现象**：C 程序里一用字符串常量（`puts("Hello")`），输出就是垃圾，而且不报错。
- **原因**：`link.ld` 把 `.rodata` 放在 IMEM（0x0 起），而 `lw` 只连 dmem（0x1000 起）。
  两条路完全独立，`lw` 永远不会去 imem 取数。
- **防范**：
  - 写 C 之前先确认内存模型：指令和数据是分开放的还是统一编址？
  - 看 `.dis` 里有没有 0x0~0xFFF 范围内的 `lw`——那基本一定是错的。
  - 链接脚本的内存范围和 RTL 的 imem/dmem 容量必须对得上。
- **受影响的不只是字符串**：`const` 数组、`switch` 跳转表都会进 `.rodata`。
- **档案**：`cases/case-23-rodata-in-imem.md`
- **一句话**：**`.text` 里的东西，`lw` 看不见。**

## 24. 给工具读的文件，别用相对路径
- **现象**：`iverilog` 仿真正常，Vivado 综合上板后 CPU 空转，板上毫无反应，综合不报错。
- **原因**：`$readmemh("sw/prog.hex")` 的相对路径是相对**进程的 cwd**，
  不是相对源文件。iverilog 从工程根跑，Vivado 不一定——找不到文件就静默不加载。
- **防范**：预处理阶段统一把路径换成绝对路径（`prepare_sources.py` 干这件事）。
  源头保持可移植的相对路径，综合副本用绝对路径。
- **同类**：`launch_runs` 在后台进程跑，报告前必须 `open_run`，否则报 "No open design"。
  这类 ERROR 不影响比特流生成，先看 `STATUS` 是不是 `Complete` 再慌。
- **档案**：`cases/case-24-readmemh-relative-path.md`
- **一句话**：**相对路径只对自己那套工具有效。**

## 25. 译码器输出、执行器没实现的编号，会走 `default`
- **现象**：没有现象。移位指令算出来全是 0，程序照跑，17 个 testbench 全绿。
- **原因**：`alu_ctrl` 输出 `alu_sel = 7/8/9`（`sll/srl/sra`），
  而 `alu.sv` 的 `localparam` 只到 6，`case` 的 `default: result = 0` 把它们接住了。
  **两个文件各写一份编码表，没有任何机制保证一致。**
- **防范**：
  - 译码器和执行器共用同一份编码定义（`package` / `` `include ``），不要各写一遍。
  - `default` 返回 0 是防锁存器的必要手段，但**必须配"每个操作都有单元测试"**，缺一不可。
  - 加新译码分支时，同步检查执行端——这是天生的耦合点。
- **为什么全绿也没抓到**：ALU 单元测试只覆盖了 0~6，测试程序里一条移位都没有。
  **"没测到的功能等于没有"**。
- **档案**：`cases/case-25-alu-unimplemented-opcode.md`
- **一句话**：**编码表写两遍，就是在埋雷。**

## 26. 共享 ALU 里塞大运算，会拖垮所有用过 ALU 的路径
- **现象**：加完 M 扩展乘法器，功能全对、17 个 testbench 全绿，
  但综合后 **WNS 从 +4.284ns 掉到 −0.767ns**，50MHz 不满足。
  综合不报错，照样能生成比特流——**静默生成一颗跑不动的芯片**。
- **原因**：ALU 是组合逻辑，所有运算并列。`alu_result` 既要喂分支判断
  （`branch_taken`），又要喂跳转目标（`jump_target`），
  于是**乘法器被卷进 `mem_wb → 转发 → ALU → branch_taken → next_pc → PC` 这条关键路径**。
  综合器无法证明"分支指令不走乘法"。
- **定位**：看时序报告的 `Logic Levels` 里有没有 `DSP48E1`。
  本案 33 级逻辑、含 2 个 DSP48 —— 乘法器就在路径上。
- **第一次修错了**：只把 `jump_target` 拆出 ALU，WNS 仍 −0.772，因为
  `branch_taken` 还依赖 `alu_result[0]`。**改之前要先确认路径经过哪个信号，别猜。**
- **正确修法**：给分支判断一个**专用比较器**（`==`、有/无符号 `<`），
  不再借道 ALU。跳转目标同理用独立加法器。
- **效果**：WNS 回到 **+4.215ns**，Fmax ≈ 63.4MHz，
  LUT 只多 14 个（省掉长路径反而抵消了比较器的面积）。
- **附**：同轮实测 32 位组合除法器最长路径 **82.6ns**（≈12MHz），
  50MHz 差 4 倍做不了 → 除法改走软件（`-mno-div` + `sw/div.c`）。
- **档案**：`cases/case-26-multiplier-timing-critical-path.md`
- **一句话**：**共享 ALU 是放大器；窄逻辑（分支/跳转）别和乘法器挤一辆车。**

## 27. 少数一条指令，比写错一条指令更危险
- **现象**：没有任何现象。写 C、跑 Dhrystone、上板演示全部正常。
- **原因**：`alu_ctrl` 的 I 型译码漏了 `funct3 = 011`（`sltiu`），
  落到最后的三目兜底值 `4'd0` = **ADD**。
  于是 `sltiu` 被当 `addi` 执行——不报错，结果错。
- **为什么没暴露**：测试程序是手写汇编，一条 `sltiu` 都没有；
  C 程序里也没有 unsigned 常量的比较，gcc 没生成它。
- **同类**：和 case-25（移位落到 default 返回 0）完全一样，
  **译码器输出、执行器没有，静默走兜底**。
- **顺带查出来的**：`decoder` 也缺 `0001111`(FENCE) 和 `1110011`(SYSTEM)，
  RV32I 40 条实际只有 36 条有响应。已补上（FENCE 当 NOP，
  ECALL/EBREAK 因无异常机制也当 NOP，写进论文的已知局限）。
- **防范**：
  - 按 **ISA 手册逐条打勾**，不要凭"常用的都做了"的感觉
  - 每补一条译码分支，同步检查执行端有没有对应
  - `default` 不要静默返回一个"正常值"
- **档案**：`cases/case-27-missing-sltiu.md`
