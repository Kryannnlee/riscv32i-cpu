## 第0层 · 一条指令是什么

### 问题（2026-10-30）

> 有一个盒子，里面有 32 个格子，编号 x0 到 x31，每个格子存一个 32 位数。
> 现在要让**第 1 个格子变成 5**。
>
> 你要告诉这个硬件**哪几件事**，它才知道该干什么？

### 你的回答

```verilog
data = {29'b0, 3'd5};
```

### 我的判断

**答的是"5 在 32 位里怎么表示"，不是"要告诉硬件哪几件事"。**

这个回答本身是对的：32 位的 5 = 高 29 位补 0 + 低 3 位是 101。
说明位宽、零扩展这两件事你有感觉。

但它跳过了问题的核心。这就是关键区别：

| | 是什么 | 例子 |
| --- | --- | --- |
| **数据** | 被处理的东西 | 32 位的 5 |
| **指令** | 告诉硬件怎么处理数据 | 「把 5 放进 x1」 |

硬件只收到 32 位的 5，它不知道这是要放进 x1、x2，还是拿去和别的数相加。
**所以光有数据不够，还得有一条"指令"说明拿它干什么。**

这就是第 0 层真正要建立的东西。

### 第 1 层 · CPU 为什么需要那几个部件

### 问题（2026-10-30）

> 现在有一条 `add x1, x2, x3`。
> 从"这条指令躺在内存里"到"x1 被改成新值"，中间硬件必须做哪几件事？
> 每件事大概需要什么样的部件？

### 你的回答

> add 是 r 型运算，所以肯定要寄存器，首先 if，然后 id，读寄存器，
> ex 就计算结果，然后 mem 访问内存，wb 把结果写回

### 我的判断

**阶段划分全对。** IF → ID → EX → MEM → WB，顺序没问题。

一处要纠正：

> "mem 访问内存"

`add` **在 MEM 级什么都不做**。MEM 这一级是存在的（流水线必须有第五级），
但对算术指令来说它是**空过**——只对 `lw` / `sw` 才有实际动作。

这不是抠字眼：后面讲流水线时，"每级都在干活"和"有的级空转"是同一个道理的两面，
空转的级照样占一拍。

还差一半：问题问的是**部件**，你答的是**阶段**。阶段 ≠ 部件。

### 追问 4 的回答（2026-10-30）

### 追问 4 的判断

| --- | --- | --- |
| IF | decoder | ❌ |
| ID | imm_gen、adder、alu_ctrl、program_counter | ⚠️ 部分对 |
| EX | alu_ctrl、mux、alu | ✅ |

| WB | mux、regfile | ✅ |

**后三级全对。** 问题集中在前两级的交界处。

正确对应：

| 级 | 模块 | 干什么 |
| --- | --- | --- |
| **IF** | `program_counter`、`imem` | 拿地址取指令。**这一步不知道取回来的是什么** |
| **ID** | `decoder`、`imm_gen`、`regfile`（读口） | 认指令：出控制信号、生成立即数、读 rs1/rs2 |
| EX | `alu_ctrl`、`alu`、MUX | 算 |
| MEM | `dmem`（其余空过） | 只有 lw/sw 动内存 |
| WB | `regfile`（写口）、MUX | 挑一个结果写回 |

两处纠正：

1. **`decoder` 在 ID，不在 IF。** IF 只管"按地址把 32 位拿回来"，

2. **`adder` / `alu_ctrl` 不在 ID。** `pc + 4` 属于 IF（算下一个地址）；
   `alu_ctrl` 属于 EX（它给 ALU 出操作码，ALU 在 EX）。

### 第 2 层 · 单周期：一拍里做完

### 问题（2026-10-30）

> 单周期 CPU 里，一条指令的 IF/ID/EX/MEM/WB 在**同一个时钟周期内**串行走完。
>
> 那么问题来了：**PC 什么时候更新？** 如果在这五步还没走完的时候就更新了会怎样？
> 反过来，如果更新太晚又会怎样？

### 第 2 层 · 你的回答

> ```systemverilog
> always_ff @(posedge clk) begin
>     if (rst)       pc <= 32'd0;
>     else if (!stall) pc <= pc_next;
> ```
> 上升沿触发，应该是五步走完之后到下一个 posedge 再更新

### 第 2 层 · 判断

**对的。** 补两个细节：

1. **posedge 是"这一拍结束 / 下一拍开始"的分界线。**
   五步是纯组合逻辑，在边沿**之前**必须全部稳定（这就是 setup time 的由来）。
   边沿一到，寄存器采样，新的 `pc` 从下一拍开始生效。
2. **所以"提前更新"的后果是**：`pc` 一变，`imem` 输出的指令立刻跟着变，
   而这条指令的最下游（WB 写回）还在用旧指令算出来的结果——整条通路的数据对不上。

这也解释了你前面说的"短板效应"：时钟能跑多快，由**最慢那条组合路径**决定。
单周期里最长的一条是 `lw`：

```
PC → imem → decoder → regfile读 → ALU → dmem → regfile写
```

一条路径串了六个部件，所以单周期频率上不去。

**第 2 层通过。**

### 第 3 层 · 流水线：为什么要切开

### 问题（2026-10-30）

> 把五步切开、中间插 `if_id` / `id_ex` / `ex_mem` / `mem_wb`，
> 程序就能跑得更快。
>
> 问：**单条指令从进来到写回，花的时间变短了吗？**
> 如果没变短，那"更快"到底快在哪？

### 第 3 层 · 你的回答

> 利用了空挡

### 第 3 层 · 判断

**直觉对，但只说了一半。**

"利用空挡"是从**资源利用率**看：单周期里每个部件在自己那一段用完之后就闲着，
剩下大半个周期什么也不干。流水线让每个部件每一拍都有活干。

缺的那一半是**延迟 vs 吞吐**的区分：

| | 定义 | 流水线之后 |
| --- | --- | --- |
| **延迟** | 一条指令从进来到写回要多久 | **不变，甚至更慢**（多了流水线寄存器的延迟） |
| **吞吐** | 单位时间能完成几条指令 | **约 5 倍** |

所以"更快"指的不是"这条指令更快做完"，而是"**同样时间能做更多条**"。

为什么吞吐能变 5 倍？因为**时钟能变快**：
单周期的时钟必须等最长那条路径（`lw`，串六个部件）；
切成五级后，每一拍只需要等**这一级**最慢的部分。

一句话：**单条指令没有更快，是同时在做的条数变多了。**

**第 3 层通过。**

### 第 4 层 · 切开之后为什么出错

### 问题（2026-10-30）

> 既然切开就能变快，为什么不做 50 级？切成 50 级不是更快吗？

### 第 4 层 · 问题 1 的回答

> 且寄存器本身是有延迟的，物理延迟，级数多了……

### 第 4 层 · 问题 1 的判断

**三条全对，而且就是标准答案的三条。** 补上"为什么"：

| 你说的 | 背后的量化关系 |
| --- | --- |
| 分支错了推倒重来很麻烦 | 罚的拍数 = **从取指到"知道跳不跳"之间的级数**。5 级里这个数是 2；50 级里可能变成 20 拍 |
| 级数多，两条指令配合困难 | 前后两条指令隔的级数越多，**需要的转发通路越多**，而且 `lw` 后面紧跟用它的指令时，要停的拍数也越多 |

一句话：**深度是有甜点的，不是越深越好。** 五级是经典权衡点。

补一处精度——**"不塞气泡会怎样"的具体后果**，你说的"把错误的东西送进去算"方向对，但可以更准确：

```
         C4          C5          C6
lw      EX          MEM         WB
add     ID          EX(早了一拍) MEM
                    ↑ 此刻 EX/MEM 里还是地址、mem_wb 里还是更早的数据、regfile 还是旧值

**还是没有值可用。** 必须再等一拍，让 `lw` 走到 WB、数据锁进 MEM/WB，

所以清空 `id_ex` 的本质不是"防污染"，是**把 `add` 推迟到正确的时机再放行**。

顺带一个副作用（也要清空才能避免）：`if_id` 保持着 `add`，如果 `id_ex` 不冲刷，

## 延伸讨论（2026-11-03）：能不能按指令类型省拍

用户提了两个很自然的想法。两个都值得记，因为它们正好对应现代 CPU 的两种真实做法。

### 想法 1：给 MEM 单独长周期，其他级短周期

> "难道不能专门给 MEM 给一个比较长的周期，其他的都正常，给一个短的？"

**可以，这叫"等待周期"（wait state）或多周期级。现代 CPU 就是这么干的。**

```
时钟按最快的级来定
  IF  → 1 拍
  ID  → 1 拍
  EX  → 1 拍
  MEM → 慢，给 2 拍或 10 拍
  WB  → 1 拍
```

MEM 需要多拍时，把前面几级冻住（PC 停、`if_id` 停、`id_ex` 灌气泡）——**和 load-use 的停法一模一样**。

**所以 6c 写的 `stall` 不只是给 load-use 用的，它是一个通用的"这一级需要多拍"机制。**

代价没有消失，只是转移了：

| 方案 | 时钟 | 代价 | 谁付 |
| --- | --- | --- | --- |
| 现在：时钟慢到 MEM 一拍够用 | 慢（按 lw 定） | 每条指令每一拍都慢 | **全体** |
| 想法 1：时钟快，MEM 多拍 | 快（按 ALU 定） | 只有访存指令停 | **只有访存指令** |

哪个好取决于程序里访存指令占多少。

真实 CPU 的分层（这就是"想法 1"的工业版）：

| 情况 | 需要几拍 | 处理 |
| --- | --- | --- |
| L1 缓存命中 | 1 拍 | 不停 |
| L2 命中 | ~10 拍 | 停 9 拍 |
| 主存 | ~100 拍 | 停 99 拍 |

### 想法 2：让 add 跳过 MEM，只走 4 拍

> "只有 lw 和 sw 需要读内存，其他指令不用 MEM，直接跳过，只需要 4 个周期，不行吗？"

**不行，会撞车。**

```
         C1   C2   C3   C4    C5
I1 lw    IF   ID   EX   MEM   WB
I2 add        IF   ID   EX    WB ← 跳过 MEM，想在这儿写回
```

C5 这一拍，I1 和 I2 **同时都在 WB**。而寄存器堆只有**一个写口**，一拍只能写一个寄存器 → 冲突。

想避开冲突就得让 I2 在 WB 门口等一拍，**省下的那一拍又还回去了**，而且判断逻辑更复杂。

**根本原因：流水线是一条传送带，所有指令必须同一个节拍前进。**

各级寄存器共享（`ex_mem` 只有一个）、WB 写口共享、`dmem` 共享。
一旦允许某条"快进一拍"，它就会和前面那条撞在同一个位置——像马路上车速不一就会追尾。

连 x86 那种变长指令都是先把指令拆成**等长的微操作**，再送进统一流水线，
正是为了回到"所有指令节拍一致"。

> **结论：流水线不是"让快的跳级"，而是"让慢的等"。**

### 顺带纠正：是短板效应

木桶能装多少水由**最短**那块板决定；时钟能多快由**最慢**那一级决定。
用户说成了"长板效应"，意思对，词反了。

## 关于 flush 与"能不能有多个 PC"（2026-11-03）

用户在外面对话中追问了两个问题，都问到了点子上：

1. **"104 和 108 的指令本身没错，凭什么说它们是错的？"**

   分支说"要跳"，那么顺序取来的后续指令必然不在路径上——不是猜，是逻辑必然。

2. **"只能有一个 PC 吗？能不能有多个 PC？"**
   答案：取指用的 PC 只有一个；但**每条指令会把自己的地址揣在流水线寄存器里**，
   所以同一时刻流水线里存在多个不同的 PC 值。

### 这两个问题正好解释了我们的一个设计

`if_id_pc` / `id_ex_pc` 就是"每条指令随身携带的地址"。

所以算分支目标时：

```systemverilog
assign branch_target = id_ex_pc + id_ex_imm;   // 用分支自己的 PC，不是当前 pc
```

分支进 EX 时，全局 `pc` 已经指向它后面第 2 条了。
用当前 `pc` 算目标会多跳 8 字节——这正是 `cases/case-10` 记录的坑。

### 设计边界（用户自己提出的）

> "我们得把自己框定在这样一个流水线的前置条件里面"

正确。当前架构的约束：单发射、顺序执行、单取指 PC、无分支预测、无乱序。
讨论 6d 时只在这个框里想。

## "有时相关、有时不相关"的矛盾感（2026-11-03）

用户提出一个很本质的困惑：

> 我总觉得好像每一条都是独立的，但实际上又不是，我觉得很矛盾。
> 有时候 sub 算出来的东西要给 add 用（要读寄存器），有时候又没关系。

### 答案的关键：硬件不认识"依赖"这个词

用户觉得矛盾，是因为在用**语义**思考（"这条指令要干什么"）。
硬件根本不看语义，它只做一件事：**比较编号**。

```
编号相等 + 是 lw     → 停一拍（hazard_unit）
编号相等 + 不是 lw   → 抄近路（forward_unit）
编号不等             → 什么都不做（绝大多数情况）
```

所以"独立"和"相关"在硬件里不是两种不同的东西，**是同一个比较的两种结果**。
没有矛盾，只有 `==` 成立不成立。

### 三层关系 vs 代码

| 关系 | 本质 | 代码在哪 |
| --- | --- | --- |
| 独立 | 编号不相等 | 什么都不做 |
| 数据依赖 | 编号相等 | `forward_unit` / `hazard_unit` |
| 控制依赖 | 分支跳不跳决定后面执行不执行 | `flush`（与编号无关） |

**注意最后一行**：控制依赖和数据依赖是两套完全不同的机制。
`flush` 不看任何寄存器编号，只看 `branch_taken`。

## 6d 预测验证（2026-11-03）

把 `branch_target = id_ex_pc + id_ex_imm` 改成 `pc + id_ex_imm`，先让用户预测，再跑。

### 预测 vs 实际

| # | 用户预测 | 实际 | 判定 |
| --- | --- | --- | --- |
| 1 | 目标偏移 +8（分支后第 2 条） | +8：44 → 52 变成 60 | ✅ 完全正确 |
| 2 | x11 不会得到 111/222/777，会是错值 | **x11 = 3（没变）** | ✗ 方向对，结论错 |
| 3 | `pc_redirect` 次数不变 | **3 次（期望 4）** | ✗ |

### 关键发现：测试有盲区

完整结果：

```
15 项寄存器检查全部 PASS
FAIL 改道次数 = 3，期望 4
```

**所有寄存器都是对的**，只有计数器抓到了错误。

原因：多跳 8 字节后，从 `mem[11]` 直接跳到 `mem[15]`，
正好**整个越过了** `mem[13]`（第二个分支）和 `mem[14]`（毒药）。
- x11 仍然是 3（毒药没执行，和预期一致）
- x12 仍然是 2（`mem[17]` 执行的）

**路径错了，但终值偶然一样。** 只有 `redirect_count` 能发现。

教训：**只检查寄存器终值不够，还要检查路径**（跳了几次、执行了多少条）。
